## 定位

我要在 GitHub 开源一个代理池。目标不是功能更多，而是在窄范围内做到可证明的正确：
把公开免费代理列表和免费节点订阅（不可信）与我自有或付费的代理（可信）汇成一个统一入口，
提供轮换与会话粘性，且每条对外声明都有第三方可复现的证据。

差异化命题：现有项目把上游当成“可能不稳定”，本项目把上游当成“可能作恶”，并用独立观察者证明自己说的每一句话。

## 已确认的输入

- 主要用途：通用抓取，200 并发以内，会话 10 分钟以内
- 第一版支持节点订阅
- 有少量自有或付费代理，仅作兜底

## 默认决定（要偏离请先说明理由）

- 形态：单入口正向代理网关（HTTP 代理 + SOCKS5，同端口按首字节分流），附只读管理 API 和 Prometheus 指标；
  可选提供与 jhao104/proxy_pool 相同的 /get /pop /all /count /delete 适配层
- 控制通道：代理用户名参数（会话 ID、TTL、国家、协议、信任层、换绑策略），语法贴近商业代理的通行写法；
  会话 ID 是任意字符串，不需要预先登记；另提供“端口即会话”，照顾不支持代理认证的客户端
- 必须覆盖的用法：每请求轮换、按时间或请求数轮换、粘性会话、按条件过滤、
  免费层耗尽时回落到可信层、直连规则
- 技术栈：Go，单静态二进制加多架构容器镜像（含 arm64）；默认零外部依赖（内嵌 SQLite）
- 上游协议：http、https、socks4、socks5；ss、vmess、vless、trojan 通过进程内嵌入 sing-box 的出站实现支持。
  已知缺口：sing-box 没有 xhttp 传输，也不支持 vless 新增的加密方式，普查里 7.2% 的 vless、vmess、trojan 节点因此用不了；
  遇到不支持的节点要明确报告原因，不能静默丢弃
- 许可证：GPL-3.0-or-later（因为嵌入 sing-box）；不使用 sing-box 的名称
- 配置：单个声明式文件、JSON Schema、环境变量覆盖、校验子命令、热重载；
  新增代理源或订阅只改配置不改代码
- 安全默认值：只监听回环地址；对外监听必须配置凭据，否则拒绝启动；
  直连和可信层拒绝私网与云元数据地址；
  不可信层默认只承载端到端 TLS 流量：明文 HTTP 请求默认拒绝，
  隧道（CONNECT 与 SOCKS5）的首包必须是 TLS 握手；
  探测永不关闭证书校验；要求跳过证书校验的节点默认不可用
- 非目标：不靠扫描或测绘引擎取源；不做浏览器指纹伪装；不做反向代理模式；不解密客户端的 TLS

## 第一阶段 1B：72 小时实测（进行中；服务器已提供，部署由你执行）

工具在 `research/fieldtest/`，测量口径事先写在 `research/fieldtest/PROTOCOL.md`。

1. 自建 judge 端点（HTTP 与 HTTPS，回显来源 IP 和请求头，返回固定哈希的载荷），部署在独立主机。
   这一轮只有一台服务器，judge 和探测器同机、分属两个进程；这是已知局限，写进报告。
2. 对普查到的代理和节点做不少于 72 小时的分阶段探测
   （TCP → 协议握手 → 隧道内 TLS，完整校验 → 回显 → 载荷完整性），原始记录全部落盘可查询。
3. 同时每 10 分钟保存各列表的快照，补上四个重写历史的仓库缺失的时间线。
4. 产出：各来源的实测可用率、出口 IP 与入口 IP 不一致的比例、篡改与证书异常的比例、
   实测寿命分布，并与 Mani 等（ACSAC 2018）和 Mehanna 等（MADWeb 2024）对账；
   偏差大时先怀疑自己的探测器。
5. 规范与客户端行为：以 RFC 9110、RFC 9112、RFC 1928、RFC 1929 为准；
   抓包确认 curl、Python requests、Go net/http、Node、Chromium、Firefox
   在代理认证、407 处理、连接复用上的真实行为，产出兼容性矩阵和已知坑清单。

## 第二阶段：设计必须回答

- 威胁模型与信任分层：免费代理和免费节点可窃听、篡改、做中间人；网关自身可能被滥用。
  至少三层：可信（自有或付费）、不可信已验证、不可信未验证。每层的默认策略是什么。
- 粘性契约：会话键的来源与回退顺序；绑定对象是实测出口 IP 而非代理地址；
  空闲 TTL 与最长寿命；上游失效时“报错”与“换绑并明确告知”两种策略的精确语义和告知方式；
  经 CDN 中转的节点入口 IP 与出口 IP 不同、多个节点共用一个出口时如何处理。
  写成状态机并列出不变量。
- 重试语义：隧道建立前可以换上游重试；已向上游写出请求字节后不重放；
  每次重试都记入指标。
- 选路：按“上游 × 目标注册域”估计成功率与延迟，带衰减，冷启动回退到全局先验；
  被动信号优先于主动探测；探测频率随不确定性自适应；单上游并发上限。
  至少实现并比较轮询基线、P2C 加 EWMA、Thompson 采样。
- 来源治理：每个上游记录出处；按源统计产出率、中位寿命、独占贡献并自动降权；
  失效或停更的来源自动摘除并报告；输入校验拒绝垃圾行、私网地址和重复条目；
  协议以握手实测为准，不信任列表的标签；拉取用条件请求和退避；
  记录各源许可与条款，对照 GitHub Actions 条款决定定时任务放在哪里。
- 出口 IP 观察：至少两个互相独立的观察者，其中一个是自建 judge；复测周期随上游类型调整。
- 失败分类法：连接超时、握手失败、407、目标封禁、内容被篡改、证书异常，
  各自如何影响评分与重试。

## 第三阶段：验证（必须由你我之外的东西来证明）

- 第三方观察：粘性与轮换的结论以独立主机上的 judge 访问日志
  和至少两个互相独立的公共 IP 回显服务为准
- 真实客户端：CI 中用未修改的 curl、requests、httpx、Go net/http、Node、Scrapy、
  Playwright（Chromium 与 Firefox）跑通兼容性矩阵
- 差分：同一批请求直连与经网关的响应哈希一致；
  用 HTTP Garden 式的差分用例检查请求解析歧义
- 故障注入：用 toxiproxy 和“作恶上游”夹具（篡改内容、TLS 中间人、慢速、半开连接）
  验证状态机不变量；解析器（代理行、分享链接、订阅格式）有属性测试和模糊测试；
  竞态检测与协程泄漏检测全部通过，并且在 CI 中每次提交都运行
- 对照实验：三种选路策略在同一池、同一时段交错运行，
  指标（成功率、p95 延迟、10 分钟会话保持率）和判定标准事先写定，结果给出置信区间
- 交叉校验：自家探测器与一个独立探测器（如 monosans/proxy-scraper-checker）
  对同一输入的分歧率及原因
- 可复现：公开原始探测数据、分析脚本和基准脚本，一条命令可复跑
