### D6 的已知代价

- 别人不能把本项目嵌进闭源产品。
- sing-box 够不着一部分节点。普查的 18,266 个 vless、vmess、trojan 节点里有 1,310 个（7.2%）：
  1,025 个用 xhttp 传输（其中 990 个是 vless），346 个 vless 节点的 encryption 不是 none（Xray 新增的加密方式），
  两类有重叠。这部分节点第一版用不了；解析时要明确报告“不支持”的原因，不能静默丢弃。
  数据见 `research/census/out/nodes_summary.json` 的 `transport`。
- 这个比例如果明显上升，要重新评估下面的方案 C。
- 全部可映射的节点（19,307 个，另有 1,910 个跳过校验的对照出站）已经用 sing-box 1.14.4 的 `check` 命令验过：
  只有 8 个被拒，原因是 REALITY 公钥格式不对或插件参数不认识。见 `research/fieldtest/internal/nodes/census_test.go`。

### D14 的补充（2026-11-10，报告初稿核查之后）

报告初稿经过一轮逐条核查，下面几项是核查之后补的，同样只加分析、不改 PROTOCOL 和探测器：

- **复测偏晚按是否在密集 /24 分开**（`research/phase1b/m_instrument.py` 的 `backlog.revisit_ratio.by_dense_24`）。连不上一类的复测间隔比
  p90 在 27 个小时里超过 2，要知道是不是仪器的问题。分开后几乎全在候选密集的 /24 里，与 D13 说的“同一个 /24 同时最多 4 个探访”一致。
- **证书上的组织名只列出现在至少 5 个不同代理 IP 上的**（`m_mitm.py` 的 `ORG_MIN_IPS`，`m_posthoc.py` 的签发者组织同一门槛）。
  只在一两个 IP 上出现的名字能把一家真实机构和一个具体的开放代理对上号，这和“不输出第三方主机名”是同一类问题；Zscaler、mitmproxy 这类出现在很多 IP 上的名字照列。
- **与 Mani 等的 1.06% 对账用全部隧道协议**（socks5 / socks4 / connect），只算 CONNECT 的另给。原文经 CONNECT 和 SOCKS 两种代理测 HTTPS。
- **内容完整性模块与 fieldtest 对齐两处口径**：同一请求头出现两次时取最后一个（`derive.go` 读进 map，后写的覆盖先写的）；
  回显服务与 judge 的出口比对按记录流的顺序累积出口集合（summary.go `observer_vs_judge`）。两处都是分析脚本自己的口径与 fieldtest 不一致，不是事后加的新口径。
- **`m_availability` 判定密集 /24 也按“状态文件 ∪ 尝试记录”数**，与其他模块一致；`report_tables.py` 逐个 /24 比候选数，不只比集合。
- **PROTOCOL 没写、分析模块自己定的解释，报告里一律标出**：标签的严格映射；按候选取最严重一层时“冒充 judge > 去向不明”的次序；
  “新上榜”“确认死亡”的具体判法（各模块 `definitions`）。

核查还查出两处 PROTOCOL 与探测器代码不一致，测量开始前就是这样，72 小时内没改，报告里如实写出：聚合器的列表每 6 小时抓一次
（PROTOCOL 写每 10 分钟抓一次各列表），节点约每 30 分钟一轮（PROTOCOL 写每 60 分钟）。下次测量前要么改代码、要么改 PROTOCOL，记在 `docs/HANDOFF.md`。
