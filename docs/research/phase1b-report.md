## 结论摘要

一句话：公开列表只能当候选来源；不可信的上游只能承载端到端 TLS，并且必须完整校验证书；
按“代理地址”（ip:port）算的比例会被少数在列表里有几百个端口的 IP 左右（事后分析，D14），设计和报告都要同时按 IP 看。

1. **能用的很少，活得很短。** 常规列表里探访过的条目，72 小时内用成过一次的 33,325/79,149（42.1%），
   但任一时刻在榜条目里能用的只有 6.2% 到 9.2%（每 6 小时一点；结束时 1,847/29,701（6.2%））。
   中位寿命 0.47 小时（分辨率 20 分钟），24 小时后还活着的 3.7%；确认死亡的有 19,613/30,775（63.7%）后来又活过来。
2. **列表不是健康信号。** 新上榜、10 分钟内完成第一次探访的条目，第一次就能用的只有 2,989/27,326（10.9%）。
   下榜时已经死了的，从最后一次可用到下榜的中位数是 692.9 分钟（按下榜事件算；每个候选只算第一次下榜是 160.3 分钟）。
   下榜后 24 小时内还能用过的事件 52,686/155,787（33.8%），但多数事件在这 24 小时里又上了榜；
   只算没再上榜的是 7,763/30,240（25.7%，事后），去掉候选密集的 /24（分析时额外给）只有 469/4,258（11.0%）。
3. **协议标签不可信。** 曾经能用的条目里，按标签说的协议实测通过过的 46,955/73,941（63.5%），约三分之一用的不是标签说的协议。
   这是严格映射，映射是分析时定的；按探测器自己的宽松映射是 56,910/73,941（77.0%）。
4. **明文会被动手脚，TLS 被拦截时校验都能发现。** 隧道里遇到过中间人的候选 18,383/38,286（48.0%），
   但链有效、公钥却不是 judge 的证书，隧道建立过的 42,607 个候选里一个也没有：本次看到的拦截，正常的证书链校验全部能拦下。
   明文正文不符的代理 17,419/33,660（51.7%），几乎全是整页替换；真正在页面里注入或改写的只有 11 个代理。
   judge 收到过它转发请求的代理里，请求头带出探测器地址的 7,734/9,895（78.2%）。
5. **按候选算的比例被少数 IP 左右（事后分析）。** 候选最多的 20 个 IP 占了全部探访过的候选的 31,701/92,534（34.3%）。
   同一分母成对看：中间人按候选 18,383/38,286（48.0%），按 IP 312/10,686（2.9%）；
   HTTP 转发的 HTML 测试页正文不符按候选 17,313/26,673（64.9%），按 IP 451/8,647（5.2%）。
   按候选算的中间人几乎全来自约 90 个在列表里各有 100 个以上端口的 IP，其中 86/90（95.6%）落在 AWS 公布的地址段里。
6. **出口地址常与入口不同，也不总是稳定。** 能用的代理里出口与入口全部不同的 27,493/35,260（78.0%），但这主要来自候选密集的 /24：
   去掉它们后（分析时额外给）全部不同 6,790/14,244（47.7%），全部相同 7,330/14,244（51.5%）。
   至少有 3 次成功请求的代理里，只有一个出口的 11,801/20,882（56.5%），去掉密集 /24 是 9,719/12,676（76.7%）。
   HTTP 转发、可用、judge 收到的请求里 255,850/355,670（71.9%）经 Cloudflare 转发（事后）。
7. **免费节点：要求跳过证书校验的代价很小。** 探测过的节点严格校验下可用 6,584/21,046（31.3%）；
   只有照链接跳过校验才能用的 157 个，占曾经可用的 157/6,741（2.3%）。
8. **聚合器独有的条目：累计可用率低，时点可用率反而高。** 累计 1,935/13,379（14.5%），低于常规列表的 42.1%；
   结束时刻 1,921/13,379（14.4%）能用，高于常规列表的 6.2%（两者分母不同，见问题 8）。
   可用过的几乎一直可用（24 小时仍存活 98.4%，分辨率 60 分钟），原因本次没有查。

仪器本身：不变量没有一次违反，对照探测 4,373/4,373 和 875/875 全部成功，没有中断。
两处调度与 PROTOCOL 写的不一致（聚合器的列表每 6 小时才抓一次，节点约每 30 分钟一轮），测量开始前就是这样。
运行中段连不上一类的复测常常偏晚，几乎全在候选密集的 /24 里。与 fieldtest 自带汇总的不一致全部查明来自汇总自身漏读的文件。见“数据与仪器”。

## 对设计的含义

PROTOCOL 的每个问题都对应一项设计决定。下表是本次数据给出的回答，第 3 阶段的设计文档以它为输入。

| 问题 | 设计决定 | 数据给出的回答 |
| --- | --- | --- |
| 公开列表里的条目有多少能当代理用，各来源差多少 | 默认启用哪些来源，来源怎样降权 | 任一时刻只有 6.2% 到 9.2% 能用；各来源的累计可用率从 20.3% 到 78.9%，时点可用率从 1.5% 到 43.1%。能用的条数大体随列表变大而变多，可用率却与规模关系不大。来源要按实测产出排序和降权，不能按列表规模 |
| 能用的代理能用多久 | 粘性会话的时限，复测的频率 | 常规列表的中位寿命 0.47 小时（分辨率 20 分钟），与 10 分钟的会话（决策 D2）相差不到一个数量级：会话期间上游失效不少见，换绑语义必须事先定好（10 分钟内的失效率本次没有测）。确认死亡的多数会复活，失败要退避重试，不能永久剔除 |
| 列表更新是否及时 | 以列表为准还是以实测为准 | 以实测为准。上榜不代表能用，下榜不代表已死 |
| 列表给的协议标签准不准 | 协议是否必须以握手实测为准 | 必须。曾经能用的条目里约三分之一用的不是标签说的协议 |
| 多少代理会改内容、冒充 TLS、改请求头、带出地址、重放 | 不可信层默认只承载端到端 TLS 是否必要 | 必要。带出客户端地址很常见（按 IP 7,173/8,369（85.7%），事后）；整页替换按候选常见，按 IP 是 254/8,647（2.9%）（事后）；真正注入或改写的只有 11 个代理。TLS 拦截全部被正常的证书校验拦下，所以不可信层只放行完整校验的端到端 TLS |
| 出口地址与入口是否相同、是否稳定、不同目的地是否一致 | 粘性会话绑定“实测出口地址”是否成立 | 成立，而且必须：入口地址说明不了出口。同一个代理会换出口；经 Cloudflare 转发的，judge 看到的是 Cloudflare 的地址（按请求头推断，事后）。免费节点的出口也常与入口不同（按请求 39.2%），经 CDN 中转、多个节点共用出口的情况本次没有区分。绑定要允许出口变化，变了要明确告知 |
| 免费节点有多少可用，严格校验证书会损失多少 | 要求跳过证书校验的节点默认不可用，代价有多大 | 代价约 2.3%，默认不可用。另外 vless、vmess、trojan 节点里有 8.4% 探测不了，其中 sing-box 不支持的 xhttp 和 vless encryption 两类占 7.9%（决策 D6 的已知代价） |
| 聚合器独有的条目有多少可用 | 聚合器默认关闭是否合理 | 可用率数据撑不起“默认关闭”：独有条目累计可用率低，时点可用率反而高，能用的那部分很稳。开不开留给第 3 阶段按探测成本定，开的话照样按实测降权 |

### 与 PROTOCOL 不一致的两处调度

PROTOCOL 写的调度与探测器代码有两处不一致。两处在测量开始前就是这样，72 小时内没改（实测开始后不改口径），
这里如实报告；下次测量前要么改代码、要么改 PROTOCOL，记在 `docs/HANDOFF.md`。

- **聚合器的列表每 6 小时抓一次**，不是 PROTOCOL“组成”一节写的“每 10 分钟抓一次各列表”（`research/fieldtest/internal/probe/prober.go` 的 `snapshotLoop`）。
  常规列表每个文件抓了 438 次，聚合器每个文件 13 次，都等于各自的期望次数（`out/report.md` 附录“快照完整性”）。
  聚合器抽样只做一次（PROTOCOL），问题 8 的数字不受影响；受影响的是聚合器列表本身的时间线，只有 6 小时的粒度。
- **节点约每 30 分钟一轮**，不是 PROTOCOL 写的每 60 分钟：代码在每次抓订阅（每 30 分钟）之后就开一轮（`internal/probe/nodes.go` 的 `Run`）。
  140 轮，轮间隔中位数 30.0 分钟。可用节点的复测、不可用节点“隔 1、2、4、6 轮”的退避，在时间上都只有 PROTOCOL 写的一半。
  问题 7 的“曾经可用”因此只会偏高，幅度**未验证**。

brief 1B 第 3 条要求每 10 分钟存快照，补上四个重写历史的仓库缺的时间线（第一阶段报告）。这 72 小时里，
monosans/proxy-list 和 xyzs996/free-proxy-health-list 每个文件抓了 438 次，有 10 分钟粒度的时间线；
ErcinDedeoglu/proxies 和 gfpcom/free-proxy-list 的 wiki 是聚合器，每个文件 13 次，只有 6 小时粒度。快照在原始数据里，不进仓库。

### 仪器核对

全部通过，个别项有解释（`out/report.md` 第二节，`out/instrument.json`）：

- 测量机上的仪器自检（PROTOCOL“对照与自检”：有任何一项不符，数据不可信）：正式起点之前的预检（2026-11-06T08:05:07Z）里，
  仪器自检共核对 199 项、0 项不符，预检用的 sing-box 是 1.14.4，预检结论失败 0 项、注意 0 项（`out/instrument.json` 的 `preflight`，
  取自 `fieldtest pack` 打出的数据包里的 `preflight.txt`）。`preflight.txt` 不记探测器版本，它与正式测量是同一个二进制，是按时间先后推断的，**未验证**。
- 不变量（judge 收到、TLS 内请求一致、ClientHello 指纹、节点出口不是本机、回显与 judge 日志一致）没有一次违反。
- 对照探测：回环和公网的 judge_http、judge_tls 各 4,373/4,373，两个外部回显服务各 875/875，都是 100%，实际次数等于期望次数。
- TLS 校验通过（钉扎的隧道）之后 HTTP 阶段出错的 3,719 次（分母 689,213）。按原定义，内容层 707 次，全是正文不符；
  这 707 次收到的正文都恰是期望正文的前缀（代理提前断开）。把这种情况归“截断”、不算仪器异常是事后加的（决策 D14），
  这样归完后内容层 0 次。其余 3,012 次是超时、断开这类连接层的失败。
- 连接速率：按分钟分桶有 205 分钟超过 40 条/秒，但按 10 分钟分桶的峰值 40.0 条/秒没有超过令牌桶允许的 40.07 条/秒
  （40 条/秒、桶容量 40，允许短时突发；节点预检的时间戳在排队之前记下，会落到前一个分钟桶）。没有违反 PROTOCOL 的限速。
- 证据文件有存储上限（每个候选 12 份、总共 1 GB），超限不保存：正文缺 10,990/530,616（2.1%），证书链缺 219/262,808（0.1%）。
  依赖证据正文的判断（https 链接被改、judge 说明页）因此偏少。中间人细分用的是证书链，不用正文：
  代理到 judge_tls 的中间人尝试里证书链没存下的 169 次中，138 次凭 TLS 错误类别已按判据归入冒充 judge；
  其余 31 次（4 个候选）判不了链，按 PROTOCOL 1.2 单独计数、不并入各层，这 4 个候选都另有能判链的尝试（`out/mitm.json` 的 `layers`）。
- 与 fieldtest 自带汇总 `summary.json` 的交叉核对：仪器核对有 5 项不一致，内容完整性、节点、文献对账三个模块另有一些。
  原因是 `summary.json` 自己漏读了文件：它在 08:59:58 生成，读到 judge 当时那一小时的日志时，judge 正好整点把文件压缩改名，
  读取函数跳过了消失的文件，整个小时的 judge 记录都没算进去。把那一小时的文件，连同汇总生成之后 judge 才写下的下一小时的文件（停机后零星几条），在库里藏起来、原样重跑各模块后，全部模块的不一致都消失
  （`crosscheck_as_summary_saw.py`，结果在 `out/rotation_check.json`）。分析脚本读的是数据包里的全部文件，不受漏读影响。
  这是汇总程序的一个坑，记在 `research/phase1b/SCHEMA.md` 坑 20。核对中还发现内容完整性模块有两处与 fieldtest 的口径不同
  （同一个请求头出现两次时取哪一个；观察者看到的出口与 judge 的出口集合按什么顺序比），已改成与 fieldtest 一致。

### 启动积压

PROTOCOL 第 1.2 版要求写明启动后的积压。探测器从空状态启动（恢复的候选 0 个）；起点后 5 分钟的第一条运行状况记录里，
候选池有 40,946 个条目，其中 37,333 个还没探访过；整个窗口里池子最大是 75,283 个（2026-11-07T10:21Z）。

- 复测间隔与设定间隔之比（按前一次探访所在的小时和那次探访后的状态分组）：起点那一小时，可用一类的 p90 是 1.84、
  连不上一类是 1.44，中位数都在 1.00 左右；可用一类从第二个小时起 p90 最高 1.015。
- 连不上一类不是启动积压的问题：它的 p90 在 27/73 个小时里超过 2（第 5、8、9、15、21 到 23、28 到 47 小时），
  最高 7.76（第 34 小时），比起点那一小时严重得多。这些偏晚的复测几乎全在候选密集的 /24 里（看过数据以后加的分解）：
  连不上一类间隔比超过 2 的对子，在密集 /24 里是 76,966/135,646（56.7%），在其他 /24 里只有 113/790,708（0.0%）；
  去掉密集 /24 后，没有一个小时的 p90 超过 2（最高 1.406）。密集 /24 里可用一类也有 10,169/55,660（18.3%）的复测晚了一倍以上。
  这与决策 D13 说的“同一个 /24 同时最多 4 个探访”一致（PROTOCOL“频率与限速”）；为什么集中在这些小时，没有再查。
- 连得上但不可用一类的中位数在最后两个小时（第 71、72 小时）是 1.124，超出 0.9 到 1.1；其余各类、各小时的中位数都在这个区间里。
- 节点的第一轮用了 80.92 分钟，之后各轮的中位数是 11.61 分钟。
- 10 分钟内完成第一次探访的新上榜条目里，第一次探访的延迟：起点后 1 小时内上榜的（155 条）p50 5.9 分钟，
  之后上榜的（27,171 条）p50 0.9 分钟。这个分布在 10 分钟处截断：可探测的新上榜 54,217 条里，
  晚于 10 分钟的 24,262 条和没探访到的 2,629 条不在其中，它们几乎全在候选密集的 /24，见问题 3。

起点那一小时的积压影响的是那一小时的复测间隔和寿命分辨率。运行中段密集 /24 里连不上一类复测偏晚，会推迟这些候选的死亡确认、
少看到死而复生，也让时点可用率用到的“最近一次探访”更旧；影响有多大**未验证**。
整个窗口里，曾经可用的条目第一次失败后的复测（设定 5 分钟）p90 是 5.63 分钟（`out/lifetime.json` 的 `retest_interval`）。

### 1. 公开列表里的条目有多少能当代理用，各来源差多少

能用的比例取决于怎么问：72 小时内用成过一次的不少，任一时刻能用的很少。

| 分组 | 探访过 | 连得上 | 有协议回应 | 累计可用 | 时点可用（结束时刻） |
| --- | --- | --- | --- | --- | --- |

常规列表里很短，但死了的多半会回来。

- 聚合器抽样里可用的条目每 60 分钟复测一次（常规列表 20 分钟），短于 1 小时的中断看不到，1 小时以内的存活率没有意义；

### 4. 列表给的协议标签准不准

不准。下面用的严格映射（http → HTTP 转发，https 和 connect → CONNECT，socks4/5 → 自身）是分析时定的解释：
PROTOCOL 没规定标签对应什么协议，探测器自己对 http 标签会先试转发和 CONNECT 两种。严格映射下：

| 标签 | 探访过 | 实测通过过 | 占曾经可用的 | 去掉密集 /24：探访过 | 实测通过过 | 占曾经可用的 |
| --- | --- | --- | --- | --- | --- | --- |
| http | 37,261 | 9,359/37,261（25.1%） | 9,359/18,076（51.8%） | 29,599 | 8,597/29,599（29.0%） | 8,597/13,032（66.0%） |
| https | 48,086 | 13,460/48,086（28.0%） | 13,460/20,601（65.3%） | 30,363 | 8,442/30,363（27.8%） | 8,442/11,851（71.2%） |
| connect | 17,418 | 13,506/17,418（77.5%） | 13,506/13,804（97.8%） | 8,202 | 7,158/8,202（87.3%） | 7,158/7,389（96.9%） |
| socks4 | 23,111 | 1,538/23,111（6.7%） | 1,538/7,144（21.5%） | 20,031 | 1,453/20,031（7.3%） | 1,453/5,993（24.2%） |
| socks5 | 54,563 | 9,092/54,563（16.7%） | 9,092/14,316（63.5%） | 24,797 | 1,143/24,797（4.6%） | 1,143/5,598（20.4%） |
| 合计（候选-标签对） | 180,439 | 46,955/180,439（26.0%） | 46,955/73,941（63.5%） | 112,992 | 26,793/112,992（23.7%） | 26,793/43,863（61.1%） |

去掉密集 /24（PROTOCOL 1.2 要求另给的一组）后变化最大的是 socks5：曾经能用的 socks5 条目通过 SOCKS5 的从 63.5% 降到 1,143/5,598（20.4%），
socks5 标签的准确率主要是密集 /24 撑起来的；合计从 63.5% 变为 61.1%，没通过标签所说协议的仍在三分之一以上（去掉后接近四成），“标签不可信”的结论不变。

“占曾经可用的”把“代理死了”和“标签错了”分开。严格映射下，曾经能用的 http 条目近一半没通过 HTTP 转发，但其中多数 CONNECT 通过了；
转发了但内容被改的也算没通过，所以这一列把篡改也算进了“标签错”。按宽松映射（探测器为该标签先试的协议集合），
曾经能用的 http 条目通过过的 16,516/18,076（91.4%），合计 56,910/73,941（77.0%）；全部候选-标签对是 56,910/180,439（31.5%）。
socks4 两种映射一样，曾经能用的近八成用的不是 SOCKS4。
标 https 的候选另测了代理端口本身说不说 TLS（只握手，不发数据）：做过这项测试的 29,250 个里说 TLS 的 8,113/29,250（27.7%），
其中 4,263 个明文 CONNECT 也通过过，3,843 个 CONNECT 和转发都没通过过。探测器不经 TLS 走代理协议，
所以这 3,843 个里有没有真正只接受 TLS 的 HTTPS 代理、严格映射因此低估了多少，**未验证**。

**对设计的含义**：协议以握手实测为准，标签只决定先试哪个。

明文不可信，TLS 被拦截时正常校验都能发现。请求头、重放、出口以 judge 的记录为准；正文是否被改由探测器比对正文哈希。

- **中间人几乎都是“冒充 judge”**（三层细分是看过数据以后加的，D12）：代理用 judge 的名字现签证书，链校验不过。按候选取最严重一层，“被送到别的网站”0 个，“去向不明”73 个
  （去掉密集 /24 后冒充 judge 383/435（88.0%），去向不明 52/435（12.0%））。“冒充 judge 比去向不明严重”这个次序是分析模块定的，PROTOCOL 没有规定；
  不互斥地数，遇到过去向不明的拦截的候选有 1,247 个（去掉密集 /24 是 65 个）。
  没有一个代理拿出过链有效、但公钥不是 judge 的证书，所以本次看到的拦截，正常的证书链校验全部能拦下。
- **正文不符几乎全是整页替换**。全部协议、全部载荷的整页替换尝试 99,894 次；其中 HTTP 转发的 HTML 测试页 67,269 次，
  28,864 次（42.9%）是 judge 自己的说明页：代理把请求路径丢了，向 judge 要了“/”（事后分析）。
  真正在页面里注入或改写的（局部改动）只有 11 个代理。
- **请求被改几乎全是 Accept-Encoding**：被改过的 2,296 个代理里 2,256 个改过 Accept-Encoding，其余各项都只有 1 到 39 个代理。
  Accept-Encoding 被改的请求几乎全经过 Cloudflare：HTTP 转发、可用、judge 收到的请求里，被改的 255,866 次中 255,850 次经 Cloudflare，
  涉及的 2,224 个候选里 2,222 个（事后，D14）。所以这一行多半量的是 Cloudflare 规整 Accept-Encoding，不是代理运营者在改请求头。
- **https 链接被改成 http（SSL 剥离）**：有 1 个代理做过，3 次请求，每次都把页面里 10 处指向 judge 的 https 链接全改成了 http（共 30 处）。
  Mani 等没有发现这种代理。这个数只在局部改动的正文里数（事后，D14）：整页替换的正文里出现 `http://<judge>/` 的 26,054 次请求多半是代理检测页回显了请求地址，
  局部改动里另有 36 次是给链接加了前缀、https 一个没少，这两类都不算剥离。证据有上限、改成别的主机名数不到，这两点只会让它偏少；
  但如果一份局部改动的正文既删了 https 链接、又在别处加了 `http://<judge>/`，删掉的会被算成剥离，所以它不是严格的下限。本次计入的 3 次请求都是 10 处全改。
- **匿名程度**（HTTP 转发、可用、judge 收到，按代理取最差一级）：透明 7,648/9,654（79.2%）、匿名 1,150/9,654（11.9%）、高匿 856/9,654（8.9%）。
  探测器发 HTTP 转发请求时自己带一个 Proxy-Connection 头，代理原样透传就会被判成“匿名”（判为匿名的请求里有 12,210/33,232 是这样），

- 重放极少：judge 收到不止一次的 nonce 160/1,115,968。

**对设计的含义**：不可信层默认只承载端到端 TLS，并完整校验证书链。明文 HTTP 经免费代理，内容会被替换，客户端地址多半会被带出去。

  （一个节点可属两类）。只有 1 个出口地址的 4,988/6,741（74.0%），4 个以上的 1,393/6,741（20.7%）。
  不同的那部分有多少是经 CDN 中转、有多少节点共用一个出口，本次没有区分，**未验证**。
  同一探访里 judge 与回显服务看到的出口全部相同的 26,834/39,700（67.6%），口径与上表最后一行不同（那一行只比两个回显服务），不能直接比。

**对设计的含义**：粘性会话绑定实测出口地址，而不是代理地址；出口会变（按目的地还是按时间，本次分不开），所以绑定要持续观察，出口变了要明确告知。
多个上游共用一个出口时要当作同一个出口处理（经 Cloudflare 转发的是不是这种情况，本次**未验证**）。

### 8. 聚合器独有的条目有多少可用

聚合器独有（从没出现在任何常规列表里）的条目，累计可用率 1,935/13,379（14.5%），低于常规列表的 33,325/79,149（42.1%）；
结束时刻的时点可用率 1,921/13,379（14.4%），反而高于常规列表的 1,847/29,701（6.2%）。两个时点比例的分母不同：
聚合器是全部独有条目（抽样只做一次），常规列表是结束时在榜的条目。四个聚合器之间差别也大（累计）：
SevenworksDev/proxy-list 925/4,482（20.6%）、ErcinDedeoglu/proxies 754/4,351（17.3%）、gfpcom/free-proxy-list (wiki) 299/4,739（6.3%）、
dpangestuw/Free-Proxy 0/17（0.0%）。

能用的那部分非常稳定：寿命分析里聚合器抽样的条目 24 小时后仍存活 98.4%，结束时最近一次探访可用的 1,921 个几乎等于可用过的 1,935 个。
聚合器条目每 60 分钟复测一次，寿命的分辨率是 60 分钟，比常规列表粗，短于 1 小时的中断看不到；但差距大到分辨率解释不了。
为什么这么稳（是不是同一个运营者、是不是付费代理的泄露），本次没有查，**未验证**。

**对设计的含义**：可用率数据撑不起“默认关闭”：独有条目累计可用率低，时点可用率反而高，能用的那部分很稳。
开不开留给第 3 阶段按探测成本（每个聚合器抽 5,000 条要持续复测）定；开的话照样按实测降权。

## 已知局限

- **judge 和探测器在同一台机器上**，分属两个进程（`docs/brief.md` 1B 第 1 条，这一轮只有一台服务器）。judge 的公网地址就是探测器的出口地址，
  代理能看出“目的地就是请求者自己”。会不会有代理因此表现不同，本次无法判断，**未验证**。
- **只有一个观测点**，在一个云厂商的一个地区。对某些地区封锁或放行的代理，结果会不同。
- **诱饵站不是真实站点**。针对特定网站的注入、改广告 ID 这类行为测不到，局部改动的比例是下限。
- **明文载荷只有 HTML、JavaScript 和二进制三种，不含可执行文件**（PROTOCOL“已知局限”），看不到给下载的程序打补丁这类行为；
  问题 5 和“与文献对账”里的局部改动都不包括它。
- **只测 IPv4、只测 TCP**（PROTOCOL“已知局限”）。列表解析只认 IPv4 的 `ip:port` 写法，IPv6 的行记为不合格行，进不了候选池
  （`research/fieldtest/internal/lists/lists.go` 的 `parseLine`；`internal/probe/sched.go` 的 `ineligible` 对非 IPv4 地址再拦一道），本文说的“条目”都是 IPv4。
  节点链接里直接写 IPv6 地址的在预检时跳过（`skip_ipv6`），按最近一次预检是 27/27,801（0.1%）；主机名只解析得到 IPv6 的，
  因为预检只查 IPv4 地址（`internal/probe/nodes.go` 的 `precheck`），记在“DNS 失败”里，没有单独计数，有多少**未验证**。
  两种都仍算在问题 7“占可探测”的分母里。SOCKS5 的 UDP 转发没有测。
- **寿命的分辨率是 20 分钟**（聚合器抽样 60 分钟，见 PROTOCOL 的频率表），比它短的中断看不到（PROTOCOL“已知局限”）。
- **证据有存储上限**：正文缺 2.1%，证书链缺 0.1%。依赖证据正文的判断（https 链接被改、judge 说明页）偏少；中间人细分里判不了链的单独计数。
- **“https 链接被改成 http”只数得到改成 http://judge 的情形**，改成别的主机名数不到；计法在少数情况下也会多数（见问题 5）。
- **两处调度与 PROTOCOL 不一致**（聚合器列表、节点轮次），候选密集的 /24 里连不上一类复测偏晚，见“数据与仪器”；后者的影响**未验证**。
- **同一时段只测了一次 72 小时**，没有覆盖不同季节、不同星期。
- **原始数据没有公开**：第三方只能核对脚本、自检和 `out/` 与本文是否一致，不能从原始数据复跑（见“复现”）。
- fieldtest 自带汇总会漏读跨整点轮转的文件（SCHEMA 坑 20）；状态文件里的 `group` 只降不升（坑 21）。两者都不影响分析脚本的结果。
- 分析脚本在 Python 3.11 和 Python 3.13 上跑过自检，真实数据只在 Python 3.13 上跑过；Python 3.10 没有跑过。

## 复现

原始数据（`fieldtest pack` 打出的数据包和状态文件）含第三方地址、证据正文里有 judge 的联系方式，不进仓库，目前也没有别的公开渠道。
所以第三方现在能复现的只到这一层：读分析脚本，跑各模块的 `--selftest`，用 `check_report_numbers.py` 核对本文的数
（一位整数、代码、日期和脚本里列明的几个 PROTOCOL 常量除外）都能在 `out/report.md` 和 `out/*.json` 里找到；它只查数值是否出现，不查出自哪一项、分母对不对。从原始数据重算 `out/` 做不到，`out/` 里的数本身第三方无法独立复核。
