# 砍掉的、偏离的、否决的、还不确定的

题目的规矩是“默认决定要偏离请先说明理由”“宁可砍功能，也不留下无法验证的声明”。这一篇把这些地方集中列出来，方便一次看完、一次否决。

**2026-11-11 定下来了**：用户把这一篇里待定的事交给 Claude 按最佳实践决定，条件是砍掉的功能要给以后的版本留下扩展的余地（决策 D19）。结果：

- 砍掉的功能照砍，每一项都写明了留给以后的扩展点（下一节最后一列和“扩展点”一节）；第一版的代码要按“扩展点”一节的约束写，验收里有对应的检查。
- 与题目的偏离全部保持。
- 聚合器改成**出厂关闭**、配置一行打开，预实验查清那批稳定条目的来历以后再议（[05-routing.md](05-routing.md) 的 DD-39）。
- 主机和代理照旧由用户准备（最后一节）。

## 砍掉的功能（第一版不做）

| 功能 | 题目里的位置 | 为什么砍 | 以后要做需要什么、扩展点在哪 |
| --- | --- | --- | --- |
| 按国家选出口 | 控制通道的参数“国家” | 判断出口在哪个国家要靠第三方的地理库，它准不准本项目证明不了；写了就是一条无法验证的声明。用户名里写 `country` 会得到 403 `kaoju-bad-username`，不会被悄悄忽略 | 一个能用独立观察验证的地理来源，以及对应的验收标准。扩展点 DD-43（参数登记表）、DD-44（出口属性和选路过滤） |
| 与 jhao104/proxy_pool 相同的 `/get`、`/pop`、`/all`、`/count`、`/delete` 适配层 | 默认决定里的“可选提供” | 它把不可信的上游地址直接交给调用方，调用方绕过网关去连，本项目的全部保护（只承载 TLS、不重放、出口观察）都落空；`/delete` 还与“管理 API 只读”冲突 | 原样的适配层不做。要兼容那批调用方，可以加一组同名的只读接口，返回的是**网关自己的地址加一个会话用户名**而不是上游地址，保护不丢。扩展点 DD-47 |
| 用客户端流量试 `unverified` 的上游 | “三层各有默认策略” | 见 [01-threat-model.md](01-threat-model.md) 的 DD-2：没探测过就不知道它是不是在拦截 TLS | 不做。这是安全不变量，不是功能；层的策略集中在一张表里（DD-45），改它要先改对应的验收标准 |
| 明文 HTTP 经不可信上游（哪怕用户明确要求） | “明文 HTTP 请求默认拒绝”里的“默认” | 1B：按代理算过半会换掉正文。给一个“我知道风险”的开关，等于提供一个本项目证明不了安全的模式 | 不做；要走明文请配可信层。同上，层的策略表（DD-45）是唯一的改动点 |
| 到代理本身的 TLS（`https://` 代理）、SOCKS4 入口、HTTP/2 入口、SOCKS5 的 UDP | 没有点名 | 第 2 阶段没有测 | 先补测，再设计。扩展点 DD-46（入口和拨号都按协议登记） |
| 独占出口（一个出口只给一个会话） | 没有点名 | 做得到，但“别的使用者没在用这个免费代理”网关证明不了，独占是虚的 | 不做“独占”的承诺；需要时可以加“一个出口最多绑几个本网关的会话”的上限，只对可信层有意义。扩展点 DD-44 |
| 管理 API 的写接口、客户端回报“这个出口被封了” | “只读管理 API” | 照题目保持只读。代价：隧道里的封禁网关看不到，也没有渠道让调用方告诉它 | 需要时另议。扩展点 DD-47（接口带版本、写接口只能加在另一个监听上）、DD-48（事件带来源） |
| IPv6 的上游和目标 | 没有点名 | 1B 只测了 IPv4 | 先补测。扩展点 DD-49（地址按两种族存） |

## 扩展点

砍掉不等于堵死。第一版的代码按下面几条写，以后加回这些功能时是“加一个实现、登记一下”，不用改已有的接口和存储格式。
每一条都有 CI 里能跑的检查：[07-acceptance.md](07-acceptance.md) 的 AC-63（AC-34 的属性测试另外覆盖 DD-43 的“不认识的键报错”）。

**DD-43** 用户名参数是一张登记表：每个键登记它的名字、值的语法和默认值，解析器只认表里的键。不认识的键一律 403 `kaoju-bad-username`（不是忽略），
所以以后往表里加 `country` 这样的键是纯增加：旧的合法用户名语义不变，新键在旧版本上会明确报错而不是被悄悄忽略。

**DD-44** 出口组带一个属性表（键值对，记录每个属性的来源和观察时刻）；选路先按属性过滤、再按策略选。第一版只有“稳定与否”“层”“协议”几个属性。
地理位置以后作为一个属性加进来，前提是它有独立观察的来源；“一个出口最多绑几个会话”是同一处的一个上限参数，第一版不设（不限）。

**DD-45** 每一层（`verified`、`trusted`、`direct`）能做什么（承载 TLS 隧道、承载明文、能否重放、要不要先验首条记录）集中写在一张策略表里，
入口、拨号、转发都查这张表，不在各处各写各的判断。不变量的验收（第一节）直接对这张表和它的效果做检查。

**DD-46** 入口和拨号都按协议登记：入口是“首字节或监听配置 → 解析器”，解析器的产物统一是“账号、参数、目标”；拨号是“上游协议 → 拨号器”。
SOCKS4 入口、HTTP/2 入口、到代理本身的 TLS、SOCKS5 UDP 以后各是一个新的实现，策略、会话、选路不动。

**DD-47** 管理 API 的路径带版本（`/v1/…`）；写接口如果以后要加，只能放在另一个单独配置的监听上、用单独的令牌，只读监听上永远没有写接口。
与 jhao104/proxy_pool 兼容的接口如果要加，也走这条路，并且只返回网关自己的地址加会话用户名。

**DD-48** 事件带“来源”字段（网关自己的观察、探测、配置重载……）。以后接受调用方回报（“这个出口被封了”）时是一个新的来源，
它只能影响选路的统计、不能改出口的验证状态（调用方的话同样不可信，要与网关自己的观察分开记、分开用）。

**DD-49** 地址在存储和内存里都按“族 + 地址”存，IPv4 和 IPv6 走同一套代码；第一版在拨号和来源解析处拒绝 IPv6（明确报错），补测以后放开这一处。

## 与题目默认决定的偏离

| 题目怎么写 | 设计怎么定 | 理由 |
| --- | --- | --- |
| “会话 ID 是任意字符串” | 只能用字母、数字、下划线、点，最长 64 字节 | 第 2 阶段：出了这个字符集，用户名的字节在 curl、requests、undici 上到达代理时会变（[02-gateway.md](02-gateway.md) 的 DD-11）。连字符留作分隔符 |
| 出口观察“其中一个是自建 judge” | 运行时可选，验证时必须（[05-routing.md](05-routing.md) 的 DD-34） | 强制要求会让每个使用者先准备一台公网主机，与“默认零外部依赖”冲突。代价：没配 judge 时，探测的证书校验只有“系统根证书的完整校验”，没有公钥钉扎；出口观察的量受公共回显服务的限速约束 |
| “热重载” | 能热重载的段列了清单，监听地址和存储要重启（[06-config.md](06-config.md)） | 换监听地址要断开现有连接，客户端会自己重发请求（第 2 阶段已知坑第 8 条） |
| 聚合器“默认不订阅，等实测其独占条目再定”（1A 报告） | 出厂关闭，配置一行打开；打开时每个抽 5,000 条（[05-routing.md](05-routing.md) 的 DD-39） | 与题目一致的是“默认不订阅”；1B 显示它们值得打开，但来历没查清，预实验查过再议 |
| “符合 RFC” | SOCKS5 入口不做 GSSAPI，按 RFC 1928 的字面不是合规实现（1928-3-10） | 测过的客户端没有一个需要它；curl 会多报一个 GSSAPI 方法（矩阵 R110），但不选它也照常工作 |
| 选路“至少实现并比较”三种 | 三种都实现；出厂默认是轮询基线，直到对照实验有结论 | 没有数据之前说哪种更好都是印象 |

## 被否决的方案

| 方案 | 否决的理由 |
| --- | --- |
| 先向客户端回 200，看到 ClientHello 再去连上游 | 上游连不上时只能关连接，这是客户端最看不懂的报错，还会引来自动重发（[02-gateway.md](02-gateway.md) 的 DD-15） |
| 出口用不了时进入“已丢失”状态，直到会话过期都报错 | 免费代理确认死亡后多数会回来（[03-sticky.md](03-sticky.md) 表格）。只要出口还是原来那个，上游回来以后会话继续，并不违反“宁可报错也不换 IP”；多一个状态只会多出错的机会 |
| 粘性会话绑代理地址（proxyhub 的做法） | 入口地址说明不了出口；同一个出口背后可以有很多个代理地址 |
| 找不到同出口的上游就静默换一个（Resin 的做法） | 这正是本项目要补的空档；换绑必须是调用方选的（`onfail-rebind`），而且留下事件 |
| 按 TCP 连接认会话 | 一个会话在不同客户端上是 1 到 N 条连接（第 2 阶段已知坑第 5、6 条） |
| 用响应头告知换绑 | 隧道建成时的响应头 11 列默认都看不到（矩阵 R84） |
| 一个不可信上游说“目标不可达”就照转给客户端 | 分不清是目标的问题还是上游的问题；要两个不同出口的上游都这么说（[04-failures.md](04-failures.md) 的 DD-22） |
| 把全部候选持续探测一遍（1B 的做法） | 1B 是测量，要的是全貌；网关要的是够用。全量探测对第三方的打扰与需要不成比例（[05-routing.md](05-routing.md) 的 DD-33） |
| 参数用 `key=value;key=value` 或 URL 编码 | 等号、分号、百分号在各客户端上不保证原样到达（第 2 阶段已知坑第 3 组） |
| 配置用 JSON | 不能写注释。YAML 多一个解析库的依赖，可以接受（“只用标准库”的规矩只约束 fieldtest） |
| 口令明文写在配置文件里 | 配置文件会被贴出来（[06-config.md](06-config.md) 的 DD-41） |
| 在 GitHub Actions 上定时抓列表、探测代理，把结果当作项目的数据 | 条款上的疑问没有解决（1A 报告留给用户判断）；而且那样的数据第三方复现不了网关的行为（[05-routing.md](05-routing.md)“许可与条款”） |

## 还不确定的事

按“会不会改变设计”排序。

1. **判为“出口稳定”之后，出口还会不会变、多久变一次。** 整个粘性契约的可信度取决于它，1B 没有这个数。预实验（AC-20、AC-21）之后才知道；
   如果漂移率高到 1% 的门槛远远做不到，要回头改设计（更长的稳定观察、更短的观察期限，或者把承诺收窄到 `trusted` 层）。
2. **免费上游里有多少既能建隧道、又过得了 TLS 校验、出口还稳定。** 1B 的“可用”含只能做 HTTP 转发的；`verified` 且出口稳定的池子有多大没有数据。
   池子太小的话，200 个并发的粘性会话各占一个出口就做不到，要么共用出口，要么回落到可信层。AC-51 和预实验会给出这个数。
3. **聚合器独有的那批稳定条目是什么。** 它们撑起了粘性会话最看重的稳定性，但为什么稳没有查。
   如果它们是泄露的付费代理，用它们有没有授权上的问题，本项目现在回答不了；`CLAUDE.md` 的规矩是“不做未授权访问”，要求认证的一律不碰，但不要求认证不等于有授权。
   定下来的做法：出厂关闭，预实验查这批条目的来历（DD-39，[07-acceptance.md](07-acceptance.md)“预实验”第 6 条）。**这不是法律意见。**
4. **两个公共回显服务的使用条款**没有核对；每秒 2 次的上限能不能长期用，未验证（[05-routing.md](05-routing.md) 的 DD-35）。
5. **向上游重发 CONNECT 是否违反 9110-9.2.2-5**，是本项目的解释（[04-failures.md](04-failures.md) 的 DD-21），没有找到规范或勘误里的直接说法。
6. **设计参数。** 标了“未验证”的那些：单上游并发 8、同 IP 最多 8 个端口、目标池 3 倍并发、先验折成 2 次观察、统计半衰期 30 分钟、隔离 24 小时、来源降权的三个数、
   内容 7 天不变就停用。它们不影响不变量，只影响效果；预实验里能看的会看，看不了的留着这个标记。
7. **嵌入出站实现**还没有真正编译过（`docs/HANDOFF.md`“还没有验证过的事”）；嵌入以后单个节点的并发上限、DNS 由谁解析，要到第 4 阶段才定得下来。
8. **Go 多会话的正确写法**（每个会话一个 `Transport`）没有测；httpx、Scrapy 没有测。第 4 阶段补（AC-30）。
9. **第 2 阶段没测到的重发行为**（undici、Node 内置 `fetch` 在复用连接被关后会不会重发）。不影响设计：网关的规矩是“只关空闲连接、转发后出错回 502”，对谁都一样。
