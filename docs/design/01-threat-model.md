# 威胁模型与信任分层

一句话：上游不是“可能不稳定”，而是“可能作恶”。网关只对自己看得见、管得住的事作承诺，其余写明不防。

## 谁是对手

| 对手 | 能做什么 | 证据 |
| --- | --- | --- |
| 上游代理的运营者（免费代理、免费节点） | 看到目标主机名和端口、流量的时刻和大小；读写隧道里的全部字节；丢弃、延迟、重放；把连接送到别处；换出口；随时消失 | 明文正文不符的代理 `1B[integrity » content » all » 按代理 » 正文不符的代理（占能转发的） » num]=17,419` / `1B[integrity » content » all » 按代理 » 正文不符的代理（占能转发的） » den]=33,660`；遇到过 TLS 拦截的候选 `1B[mitm » n » 候选：遇到过中间人]=18,383`；按 IP 算，带出客户端地址的 `1B[posthoc » leak_by_ip » all » 按 IP » 带出过探测器地址 » num]=7,173` / `1B[posthoc » leak_by_ip » all » 按 IP » 带出过探测器地址 » den]=8,369` |
| 列表和订阅的发布者 | 往列表里塞任何东西：私网地址、别人的服务器、同一个 IP 的几百个端口、畸形的行、畸形的分享链接；让网关替它去探测某个受害者 | 候选最多的 20 个 IP 占全部候选的 `1B[posthoc » concentration » 探访过的代理候选 » 候选最多的 20 个 IP 合计占候选 » pct]=34.3`%；列表里有报错文本、重复行、私网地址（`docs/research/phase1-report.md`“发现”） |
| 网关的使用者（含冒充者） | 把网关当开放代理；经直连或可信层访问内网和云元数据；猜口令；耗尽连接和内存；用畸形请求制造解析歧义 | proxyhub、jhao104/proxy_pool 默认监听全部网卡且无鉴权（`docs/research/phase1-report.md`“解决得不对”） |
| 目标网站 | 封禁出口；按出口给不同内容 | 本项目没有测量，**未验证**；只作为失败分类的一类 |
| 网关与上游之间的网络 | 对免费代理这一跳，等同于上游运营者（多数免费代理的入口是明文协议） | 设计假设 |

## 要保护什么

1. **客户端流量的内容。** 不可信的上游读不到、改不了。办法只有一个：端到端 TLS，由客户端自己校验证书。
2. **凭据。** 网关用户的口令；可信层（自有或付费代理）的凭据。后者绝不能发给别的层的上游。
3. **会话的出口承诺。** 粘性会话说“这个会话的出口是 E”，这句话要么是真的，要么网关明确说它不再成立（见 [03-sticky.md](03-sticky.md)）。
4. **网关所在的网络。** 网关不能成为访问内网、云元数据的跳板，也不能被列表发布者当成扫描器。
5. **第三方。** 探测只面向公开列表里的地址，有全局限速和每个地址段的并发上限；量按“够用”定，不按“能测多少测多少”定。

## 信任分层

**DD-1** 四层，编号越大越不可信。层是上游的属性，由配置和实测决定，不由上游自己声称。

| 层 | 是什么 | 怎么进这一层 | 默认承载什么 | 默认不许什么 |
| --- | --- | --- | --- | --- |
| `direct` | 网关自己直连 | 配置里的直连规则命中 | 规则命中的目标 | 私网、回环、链路本地、云元数据地址（解析之后按 IP 判，见 INV-11） |
| `trusted` | 自有或付费的代理 | 写在配置里，带凭据 | 明文 HTTP、隧道；作兜底（决策 D4） | 同上：目标是私网和云元数据地址时拒绝 |
| `verified` | 公开来源的上游，最近一次完整探测通过 | 见下面“什么叫已验证” | 只承载端到端 TLS：隧道的第一条记录必须是 TLS ClientHello | 明文 HTTP 请求；隧道里的非 TLS 流量；80 端口的隧道 |
| `unverified` | 公开来源的上游，还没通过或已经过期 | 默认状态 | 只有网关自己的探测流量 | 任何客户端流量 |

**DD-2** `unverified` 层永远不承载客户端流量，没有开关。理由：新上榜的条目第一次探访就能用的只有
`1B[freshness » listing_freshness » 新上榜 » all » 上榜新鲜度 » pct]=10.9`%，把客户端的请求拿去试，九成是白等一次超时；
而且没探测过就不知道它是不是在做 TLS 拦截。题目要求的是“三层各有默认策略”，这一层的默认策略就是“只探测”。

**DD-3** 不可信层（`verified`）只承载端到端 TLS，明文 HTTP 请求拒绝。这是题目的默认决定，1B 的数据支持它：
明文经免费代理，按代理算过半会被换掉正文（上表）；而 TLS 被拦截时，没有一个代理拿得出“证书链有效、公钥却不是 judge 的”证书
（`1B[mitm » crosscheck » items » 证书链有效但公钥不是 judge 的 » ours.candidates]=0`，分母是隧道建立过的
`1B[mitm » n » 候选：隧道建立过（hs_ok=1 过）]=42,607` 个候选）：正常的证书链校验全部拦得下。

### 什么叫“已验证”

**DD-4** 一个上游进入 `verified`，要同时满足下面几条，而且最近一次满足的时刻在“验证有效期”之内：

1. 握手实测通过：网关按某种协议（SOCKS5、HTTP CONNECT、SOCKS4、节点协议）经它建成过隧道。协议以实测为准，列表的标签只决定先试哪一种
   （严格映射下标签说的协议实测通过过的只有 `1B[labels » accuracy » all » total » 合计（候选-标签对） » 曾经通过 » 严格 » 占曾经可用 » num]=46,955` /
   `1B[labels » accuracy » all » total » 合计（候选-标签对） » 曾经通过 » 严格 » 占曾经可用 » den]=73,941`）。
2. 隧道里与至少两个互相独立的观察者完成 TLS 握手，证书链按系统根证书完整校验通过（配了自建 judge 时另加公钥钉扎）。
   校验不过的上游标为 `mitm`，24 小时内不再进入 `verified`（见 [04-failures.md](04-failures.md)）。
3. 观察者报告的出口地址取到了，并记在这个上游名下（见 [05-routing.md](05-routing.md)“出口观察”）。
4. 它的地址不是私网、回环、链路本地、云元数据地址；它没有要求认证（要求认证的记录下来就停，从不尝试任何凭据）。
5. 节点的分享链接没有要求跳过证书校验。要求跳过的节点默认不可用；代价是曾经可用的节点里约 2.3%（`docs/research/phase1b-report.md` 问题 7）。

验证有效期是设计参数，默认 10 分钟。依据：常规列表里的代理从第一次可用起，20 分钟后还活着的是
`1B[lifetime » groups » regular » first_life_km » curve_step_20min » 1 » 1]=78.3`%，1 小时后是
`1B[lifetime » groups » regular » first_life_km » survival_at » 1h » survival_pct]=32.4`%；1B 的分辨率是 20 分钟，
10 分钟内的失效率**没有测过**。有效期取 10 分钟是在“每 20 分钟约两成失效”的前提下选的，要在预实验里核对（AC-21）。

### “已验证”不保证什么

- **不保证上游此刻还活着。** 它只说明 10 分钟内活过。
- **不保证上游不拦截客户端的 TLS。** 探测时守规矩、对客户端流量动手的上游，网关发现不了：TLS 1.3 的证书是加密的，网关不解密客户端的 TLS（题目的非目标）。
  这时保护客户端的是客户端自己的证书校验。**客户端关掉了证书校验，这一层的保护就没有了**，网关看不出来，也拦不住。README 必须写明这一点。
- **不保证匿名。** 上游知道目标主机名（CONNECT 的目标、SNI）、流量的时刻和大小，也知道网关的地址。本项目不是匿名工具。
- **不保证目标网站看到的内容没被换。** 这由 TLS 保证，不由网关保证。

## 网关自己不被滥用

**DD-5** 安全默认值，全部是“不满足就拒绝启动”或“不满足就拒绝请求”，没有警告后继续的选项：

| 规则 | 做法 |
| --- | --- |
| 只听回环 | 默认监听 `127.0.0.1`。监听地址不是回环时，没有给每个账号配口令就拒绝启动 |
| 口令 | 不允许空口令（`R69[node-fetch-env]=客户端报错`、`R131[requests,node-undici]=客户端报错`：空口令在三种客户端上本来就不能用）。口令比较用常数时间 |
| 认证失败的限速 | 按来源地址限速。407 质询本身不算失败：`R36[curl-anyauth]=6/3`，守规矩的客户端也会先不带凭据问一遍 |
| 目标地址 | `direct` 和 `trusted` 层：先解析，再按解析出的 IP 判断，再连这个 IP（防 DNS 重绑定）。私网、回环、链路本地、云元数据、多播地址一律拒绝 |
| 端口 | 见 [02-gateway.md](02-gateway.md) 的 DD-12：隧道放行的端口按层给白名单 |
| 资源 | 每个账号的并发连接上限（默认 256，不低于 6，见 DD-13）；请求头大小上限；握手阶段的超时；隧道首条记录的等待超时 |
| 管理 API | 只读，默认只听回环，与代理入口不同端口 |
| 证书校验 | 探测和转发都不关闭证书校验。代码里除自检夹具外不出现 `InsecureSkipVerify`（`CLAUDE.md`） |

## 网关不被列表发布者当枪使

**DD-6** 来源是不可信输入，按下面的规则收：

- 每个来源的条目逐行校验，拒收的按原因计数并作为指标（垃圾行、私网和保留地址、重复、IPv6、端口不合法）。
- 同一个 IP 最多收 8 个端口进候选池（设计参数），超出的记为“同 IP 端口过多、未探测”，按来源和 IP 数报告，不静默丢弃。
  依据：按候选算的中间人比例几乎全由少数各开几十到几百个端口的 IP 决定（`docs/research/phase1b-report.md` 事后分析）；
  这些端口背后是不是同一个出口，探测 8 个足以判断。8 这个数**未验证**。
- 探测有全局速率上限和每个 /24 的并发上限（沿用 1B 的做法，`research/fieldtest/PROTOCOL.md`“频率与限速”）。
  探测量按需要定：验证够用的上游就停（见 [05-routing.md](05-routing.md) 的 DD-33）。
- 订阅和分享链接的解析器只接受白名单里的字段，有属性测试和模糊测试（沿用 fieldtest 的解析器和测试）。

## 不防什么

如实列出，README 里不得声称相反的事：

1. 网关所在的主机被攻破；嵌入的 sing-box 出站实现里的漏洞（跟随上游版本，固定版本号和哈希）。
2. 上游对流量做时序分析、把目标主机名记下来或卖掉。
3. 客户端自己不校验证书。
4. 目标网站按出口封禁或投毒：网关在 TLS 隧道里看不到状态码，只能看到连接层的信号（见 [04-failures.md](04-failures.md)）。
5. 隧道建成以后，客户端在同一条隧道里发了谁的流量：Go 的一种写法会把第二个用户的请求放进第一个用户的隧道
   （`R42[go]=用了别人的隧道`），网关看不见隧道里面，防不了，只能写进文档。
6. 两次出口观察之间出口变了：粘性的承诺以观察为界，见 [03-sticky.md](03-sticky.md)“这个契约的边界”。
